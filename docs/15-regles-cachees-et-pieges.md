# 15 — Règles implicites et pièges

Ce document rassemble les **règles qu'on ne voit pas en lisant les noms des fichiers** : conventions, constantes, cas particuliers, dépendances d'ordre et comportements surprenants qui comptent pour l'exploitation, la sécurité ou l'intégrité des données. Chacune renvoie au document qui la détaille. Les défauts qui en découlent sont évalués dans [16 — Risques et dette technique](16-risques-et-dette-technique.md). La plupart de ces règles ne sont protégées par aucun test.

## 1. Identité et authentification

| # | Règle | Conséquence | Détail |
| --- | --- | --- | --- |
| A1 | **L'utilisateur est identifié par son e-mail**, pas par l'identifiant Keycloak (`sub`), qui n'est pas stocké. Le backend et les règles PowerSync font correspondre le claim `email` avec `user.email`. | Le backend normalise les e-mails (espaces retirés, minuscules) à l'inscription, à la connexion et dans la liste blanche. Changer un e-mail dans Keycloak coupe le lien avec les données. | [05](05-authentification-securite.md), [08](08-synchronisation-hors-ligne.md) |
| A2 | **Le navigateur ne parle jamais à Keycloak.** La connexion passe par `POST /api/login-user`, que le backend transforme en *password grant* avec `scope=offline_access`. Le *refresh token* est donc un jeton **hors ligne** de longue durée. | La page de connexion Keycloak (thème DSFR) n'est presque jamais affichée. Passer à ProConnect demande du développement. | [05](05-authentification-securite.md), [14](14-migration-vers-infra-ministere.md) |
| A3 | Le backend **ne signe aucun jeton**. `JWT_SECRET`, `JWT_REFRESH_SECRET`, `TOKEN_LIFETIME`, `DATAGOUV_API` et `PS_JWT_SECRET` ne servent à rien, mais `JWT_SECRET`, `JWT_REFRESH_SECRET` et `DATAGOUV_API` sont **exigées** par la validation Zod au démarrage. | Le backend et les migrations refusent de démarrer si l'une des trois manque. | [11](11-configuration.md) |
| A4 | Le même *access token* Keycloak sert pour le backend et pour PowerSync (JWKS, audience `account`). | L'émetteur et l'URL JWKS doivent être cohérents partout. La config PowerSync du dépôt pointe sur `http://keycloak:8080/realms/master`. | [08](08-synchronisation-hors-ligne.md) |
| A5 | **Liste blanche** : vérifiée seulement à l'inscription (comparaison sans tenir compte de la casse). Retirer une adresse ne désactive pas le compte. | Ce n'est pas un contrôle d'accès continu. | [05](05-authentification-securite.md), [12](12-exploitation-et-supervision.md) |
| A6 | La liste blanche est désactivée seulement si `NODE_ENV=development` est **défini explicitement**. Sans `NODE_ENV`, l'application se comporte comme en production (liste blanche et Sentry actifs). | Le README dit « inactive en développement » ; c'est vrai seulement avec la bonne variable. | [11](11-configuration.md) |
| A7 | **Administrateur** = `internal_user.role = 'admin'`, positionné à la main en SQL. Aucune route ni écran ne permet de nommer un administrateur. Les rôles Keycloak sont ignorés. | Procédure manuelle à documenter pour l'exploitant. | [12](12-exploitation-et-supervision.md) |
| A8 | Le backend crée le compte Keycloak avec `username` = nom affiché (« Prénom Nom »), mais le realm de production a `registrationEmailAsUsername` actif : Keycloak y remplace le `username` par le courriel. | Deux homonymes ne se gênent donc pas en production ; ils se gêneraient sur un realm sans ce réglage (comme le gabarit de test). | [05](05-authentification-securite.md) |
| A9 | Jeton absent ou invalide : réponse **403**, jamais 401, sauf sur `/refresh-token`. Côté client, seul un 401 au rafraîchissement déconnecte : hors ligne, la session est conservée. | Voulu pour le mode hors ligne. | [03](03-frontend-pwa.md) |
| A10 | La **déconnexion vide l'appareil** (base locale, file d'écritures, fichiers, jetons) et révoque le jeton hors ligne auprès de Keycloak. S'il reste des envois en attente, elle avertit ; hors ligne, elle est refusée. Une **session expirée**, elle, garde la base locale et la file d'écritures. | Après une session expirée, si un autre agent se connecte sur le même appareil, les écritures en attente du premier partent avec le jeton du second. | [05](05-authentification-securite.md), [08](08-synchronisation-hors-ligne.md) |
| A11 | La réinitialisation de mot de passe passe par `internal_user` (jeton UUID haché en SHA-256, 24 h, usage unique), puis le nouveau mot de passe est poussé dans Keycloak. La réponse est la même que l'adresse ait un compte ou non ; le serveur applique la politique de mot de passe. | Un utilisateur sans ligne `internal_user` ne peut pas réinitialiser son mot de passe, et rien ne le lui dit. | [05](05-authentification-securite.md) |
| A12 | **Limitation de débit** sur la connexion, l'inscription, le mot de passe oublié, les routes publiques et l'API connectée. Les compteurs sont en mémoire, par processus, et désactivés quand `NODE_ENV=test`. L'adresse IP est celle que voit le dernier des `TRUST_PROXY_HOPS` proxys. | Un redémarrage remet les compteurs à zéro ; une mauvaise valeur de `TRUST_PROXY_HOPS` fait partager une même limite à tous les agents. | [05](05-authentification-securite.md), [11](11-configuration.md) |

## 2. Services, départements et partage

| # | Règle | Conséquence | Détail |
| --- | --- | --- | --- |
| S1 | Au démarrage, le backend crée le service **`no-service`** (`visible=false`) s'il n'existe pas. Des comptes anciens y sont rattachés (ils n'ont pas de service) ; l'application leur demande de choisir un service. | Ce service doit être conservé. | [04](04-backend-api.md) |
| S2 | Le partage se fait **par service** : tous les agents d'un service voient tous ses comptes-rendus et constats. Les droits d'édition (créateur, rédacteur, délégation) sont vérifiés dans l'interface **et** par le serveur ([syncPolicy.ts](../packages/backend/src/features/sync/syncPolicy.ts)). La délégation vaut pour les comptes-rendus et les alertes de fiche, pas pour les constats, que seul leur auteur modifie. Le serveur refuse la modification d'un constat envoyé (sauf refusé par le validateur), hormis sa suppression logique. | Une table ou colonne absente de la politique d'écriture (`syncPolicies`) voit ses écritures refusées, et l'agent en est averti. | [05](05-authentification-securite.md), [08](08-synchronisation-hors-ligne.md) |
| S3 | `/api/change-service` permet à n'importe quel agent de rejoindre n'importe quel service (choix fonctionnel, chaque changement est tracé dans `transactions`). `user_dept` est recalculé depuis `service.dept_numbers` (liste séparée par des virgules). Si la liste est vide, **les départements précédents sont conservés**. Le changement de service, celui de `user_dept` et la trace sont dans une même transaction. | Les départements décident des monuments POP reçus. | [06](06-modele-de-donnees.md) |
| S4 | `user_settings` est indexé par (utilisateur, service) : changer de service fait « disparaître » les réglages, dont la validation. | — | [04](04-backend-api.md) |
| S5 | Clauses : `service_id = 'ALL'` = clause nationale. Une clause du service **remplace** la clause nationale de même `key` + `value`. Clés : `decision`, `contacts-utiles`, `bonnes-pratiques`, `type-espace`. Aucun script ne crée les clauses nationales. | Elles doivent être reprises depuis la production. | [06](06-modele-de-donnees.md) |
| S6 | Le type de service est **deviné depuis une sous-chaîne** : `id ilike '%udap%'` ou `'%crmh%'` côté statistiques, nom contenant `crmh`, `drac` ou `udap` côté interface. | Un identifiant de service mal nommé fausse les statistiques et l'affichage. | [04](04-backend-api.md), [03](03-frontend-pwa.md) |
| S7 | `suggested_email.email` est **unique au niveau global** : une adresse n'est suggérée qu'au premier service qui l'a utilisée. Les erreurs d'insertion sont ignorées. | — | [06](06-modele-de-donnees.md) |
| S8 | Tout membre d'un service peut modifier les paramètres du service (en-têtes PDF, adresses d'alerte, clauses, services instructeurs), mais seulement de **son** service ; `dept_numbers` n'est pas modifiable par ce biais. | Aucun rôle « responsable ». | [03](03-frontend-pwa.md), [05](05-authentification-securite.md) |
| S9 | Les constats envoyés d'un monument sont visibles par **tous les services** dont un département couvre ce monument (fiche et téléchargement du PDF), et non seulement par le service auteur. | Exception voulue au cloisonnement par service. | [04](04-backend-api.md) |

## 3. Données et identifiants

| # | Règle | Détail |
| --- | --- | --- |
| D1 | **Tous les identifiants sont du texte généré côté client** : compte-rendu = `report-` + UUID v4, constat et partie visitée = UUID v4, pièces jointes = UUID v7, utilisateur = UUID v7 (backend). La ligne d'un PDF a pour identifiant le **chemin du fichier**. `sent_email` et `suggested_email` réutilisent le même UUID. Les `pop_*` ont pour identifiant la référence POP. | [06](06-modele-de-donnees.md) |
| D2 | Seulement 12 clés étrangères ; la plupart des liens sont **logiques**. Presque aucun index secondaire. `user.service_id` et `report.createdBy` sont en `ON DELETE RESTRICT` : on ne supprime ni un service qui a des agents, ni un agent qui a rédigé des comptes-rendus. | [06](06-modele-de-donnees.md) |
| D3 | Dates en `timestamp` **sans fuseau** (UTC « naïf »). Certaines dates sont du **texte** (`constat_validation.created_at`, `token_expires_at`). Aucune colonne `updated_at`. | [06](06-modele-de-donnees.md) |
| D4 | **« Envoyé » = `attachment_id IS NOT NULL`**. Il n'y a pas de colonne de statut. Un constat en attente de validation ou refusé compte donc comme envoyé dans les statistiques. | [06](06-modele-de-donnees.md), [04](04-backend-api.md) |
| D5 | Suppression **logique** : `disabled = 1` pour les CR et constats (l'interface parle pourtant de suppression « irréversible »), `is_deprecated` ou `is_ignored` pour les pièces jointes. | [06](06-modele-de-donnees.md) |
| D6 | Un nouveau constat est créé `disabled=1`, `version=2`. Il n'apparaît qu'une fois un monument choisi. Les brouillons abandonnés restent cachés. | [03](03-frontend-pwa.md) |
| D7 | Formats sérialisés **sans échappement** : `preconisations` = `opt:commentaire/opt` encodé URI, `mandatory_emails` = `SERVICE:email;…`, listes d'e-mails séparées par `,` ou `;`, `personnes_presentes` séparées par `\n`, `coordonnees` = `"lat,lng"`, `reference_cadastrale` = `"SEC NUM;…"`, ancien `attachment_id` avec plusieurs identifiants séparés par `;`. | [06](06-modele-de-donnees.md) |
| D8 | Coordonnées stockées en `lat,lng`, alors que MapLibre et l'API Adresse utilisent `[lng, lat]` : l'inversion est faite à la main à chaque endroit. | [09](09-documents-pdf-cartes-emails.md) |
| D9 | Les clés de stockage ont un sens : `<parent>/images/<uuidv7>.jpg` pour les photos, `<partie>/localisation/<uuid>.jpg` pour les extraits de carte. **Le segment `/localisation/` sert à reconnaître ces images**, et **le premier segment décide de l'accès** au fichier (service du document). En base, les clés sont stockées **sans** le préfixe `attachment/`, sauf dans `attachment_redirection.s3_key`. | [07](07-donnees-externes-et-stockage.md) |
| D10 | Rien n'est jamais supprimé du stockage objet (`deleteFile` n'est pas implémenté). Chaque envoi crée un nouveau PDF. | [07](07-donnees-externes-et-stockage.md) |

## 4. Synchronisation

| # | Règle | Détail |
| --- | --- | --- |
| Y1 | La publication `powersync` est créée **vide** par `db/init`, qui ne s'exécute que sur un volume Docker neuf. Les tables y sont ajoutées par des `ALTER PUBLICATION` écrits **à la main** dans les migrations. Sur une base gérée, il faut la créer avant la première migration. | [10](10-infrastructure-et-deploiement.md), [14](14-migration-vers-infra-ministere.md) |
| Y2 | Une table ou une colonne visible du frontend doit figurer à la fois dans la publication, dans [sync-config.yaml](../powersync/sync-config.yaml) et dans le schéma local du frontend. Les évolutions doivent rester **compatibles** avec les anciennes versions de l'application en cache, qui continuent d'envoyer des écritures. | [08](08-synchronisation-hors-ligne.md) |
| Y3 | `constat_validation` n'est ni dans la publication ni dans les règles de synchro : le jeton de validation ne quitte jamais le serveur. `pop_images` et `state_report_sent_email` sont dans le schéma local mais jamais synchronisées. `user.job` est déclaré localement mais pas sélectionné. `state_report.bilan_quinquennal` reste dans le schéma local et la politique d'écriture pour les clients déjà installés. | [08](08-synchronisation-hors-ligne.md) |
| Y4 | Les pièces jointes ne se synchronisent que si `is_deprecated = 0`. Une valeur **NULL** ne le serait jamais ; la colonne vaut `false` par défaut et aucune ligne n'est à `NULL`. | [06](06-modele-de-donnees.md) |
| Y5 | Les métadonnées des pièces jointes passent par des flux **à la demande**, à l'ouverture d'un document en ligne. Les photos d'un document jamais ouvert en ligne sont indisponibles hors ligne. | [08](08-synchronisation-hors-ligne.md) |
| Y6 | Le client envoie et acquitte **une opération à la fois**, dans l'ordre. En cas d'erreur réseau ou 5xx, l'opération en cours est renvoyée plus tard ; une même erreur 4xx reçue 5 fois la met de côté. Un `PUT` sur une ligne existante est appliqué comme un `PATCH`. En cas d'erreur SQL **ou de refus de droits**, le backend répond **HTTP 200** avec `success:false` et un motif ; le client retire l'opération et la signale à l'agent. | [08](08-synchronisation-hors-ligne.md) |
| Y7 | Toute opération est d'abord copiée **en entier** dans la table `transactions` (jamais purgée, colonne `error` jamais remplie). | [04](04-backend-api.md) |
| Y8 | Conflits : **la dernière écriture reçue par le serveur gagne**, colonne par colonne. Les formulaires envoient chaque champ modifié peu après la saisie. | [03](03-frontend-pwa.md) |
| Y9 | Ordre d'envoi d'une photo : compression et contrôle du type et de la taille, puis écriture du fichier en local, **puis** insertion de la ligne. L'URL de dépôt signe le type et la taille déclarés ; un dépôt S3 en échec reste en file et repart au passage suivant. | [08](08-synchronisation-hors-ligne.md) |
| Y10 | `FORCE_REFETCH_POP=true` réécrit toutes les lignes POP : **tous les clients re-téléchargent** le référentiel. | [08](08-synchronisation-hors-ligne.md) |
| Y11 | La réinitialisation des données locales, à la main de l'agent, efface toute la base du navigateur, **écritures non envoyées comprises**. Elle est refusée hors ligne et demande une confirmation. | [03](03-frontend-pwa.md) |
| Y12 | Pas de mode multi-onglets sur iOS (pas de `SharedWorker`). | [03](03-frontend-pwa.md) |

## 5. Constats d'état, alertes et validation

| # | Règle | Détail |
| --- | --- | --- |
| C1 | Un constat devient **en lecture seule** (interface et serveur) dès que `attachment_id` est renseigné, sauf si `validation_status = 'declined'`. Seul son créateur peut le modifier, dans l'interface comme sur le serveur. Un CR est modifiable par son créateur, son rédacteur, ou un délégataire du créateur. | [09](09-documents-pdf-cartes-emails.md) |
| C2 | Correspondance alerte → service destinataire **codée en dur** : Péril → CRMH, Abords → UDAP, Objets → CAOA + CRMH, Archéologie → SRA, Site → DREAL, Biodiversité → OFB, Sécurité → Mairie. Les adresses sont recopiées depuis `service.courriel_*` à la création de l'alerte. **La colonne `courriel_mairie` n'existe pas** : l'alerte Sécurité demande toujours une saisie manuelle. | [09](09-documents-pdf-cartes-emails.md) |
| C3 | Le type d'alerte est stocké sous forme de **libellé français**. Renommer un libellé casse les données existantes. | [09](09-documents-pdf-cartes-emails.md) |
| C4 | Les alertes partent **au moment de la soumission**, **avant** la décision du validateur. Chaque alerte ne part qu'**une fois** (`sent_at`) ; une alerte en échec est reprise par la tâche périodique du backend (toutes les 15 min, 5 essais au plus) et `alerts_sent` reste faux tant qu'elle n'est pas partie. Une alerte dont la ligne n'est pas encore synchronisée part sans suivi. Les photos sont jointes jusqu'à 15 Mo au total, sinon remplacées par des liens courts. 20 destinataires au plus par alerte. | [09](09-documents-pdf-cartes-emails.md) |
| C5 | Validation (« envoi sous-couvert ») : active seulement si `user_settings.validation_enabled` **et** `validation_email` sont renseignés pour le couple (utilisateur, service courant). Jeton UUID valable 7 jours tant que la demande est en attente ; après décision, le lien ne montre plus que la décision et sa date (`decided_at`). Un refus rend le constat de nouveau modifiable. | [04](04-backend-api.md), [09](09-documents-pdf-cartes-emails.md) |
| C6 | La question « bilan quinquennal » n'est pas posée. La colonne reste en base (booléen) et dans le schéma local (texte) pour les clients déjà installés. | [06](06-modele-de-donnees.md) |
| C7 | Ouvrir l'aperçu PDF d'un constat **génère et enregistre** le plan de situation (effet de bord). Image IGN 640 × 480 au 1:5000, délai maximal 30 s. Hors ligne, le constat peut partir sans plan. | [09](09-documents-pdf-cartes-emails.md) |
| C8 | **MH complexe** : l'arbre des unités patrimoniales vient de l'API Dataspace, en ligne seulement ; hors ligne, le constat porte sur l'ensemble du monument. Les constats d'un **rapport groupé** partagent un `rapport_id` et partent ensemble : envoyer l'un envoie tous ceux du rapport. | [03](03-frontend-pwa.md), [07](07-donnees-externes-et-stockage.md) |
| C9 | Une **alerte de fiche** (`monument_alert`) est envoyée par le serveur dès que sa ligne soumise arrive par la synchronisation, ou par le navigateur de son auteur, ou par la tâche périodique : le premier qui la réserve (`sent_at`) l'envoie. L'envoi attend que toutes ses photos soient sur S3 ; après 24 h, la tâche l'envoie avec les photos reçues. Une alerte dont la ligne n'est jamais synchronisée (appareil perdu hors ligne) ne part pas. | [08](08-synchronisation-hors-ligne.md) |

## 7. Exécution, configuration et déploiement

| # | Règle | Détail |
| --- | --- | --- |
| E1 | Le conteneur backend exécute [docker-start.sh](../packages/backend/docker-start.sh) : migrations, puis serveur ; **une migration en échec arrête le conteneur**. Avec plusieurs réplicas, les migrations s'exécuteraient en parallèle. | [10](10-infrastructure-et-deploiement.md) |
| E2 | Les migrations utilisent les variables `POSTGRES_*` (pas `DATABASE_URL`) et chargent **tout** le schéma d'environnement du backend. | [11](11-configuration.md) |
| E3 | Le backend doit tourner avec `packages/backend` comme répertoire courant : les logos des e-mails sont lus dans `./public`, et le `.env` est chargé depuis `../../.env`. | [04](04-backend-api.md) |
| E4 | TLS vers PostgreSQL désactivé par défaut : `DATABASE_SSL=true` l'active pour le backend et Drizzle ; PowerSync se règle dans son YAML (`sslmode: disable` dans le dépôt). | [11](11-configuration.md) |
| E5 | Le frontend de production est servi par **`vite preview`**. La liste `preview.allowedHosts` de [vite.config.ts](../packages/frontend/vite.config.ts) est codée en dur : **un nouveau domaine exige une modification du code et une reconstruction**, sinon réponse 403. | [10](10-infrastructure-et-deploiement.md) |
| E6 | Les variables `VITE_*` sont lues **au démarrage du conteneur** et écrites dans `env.js` (public, non échappé, non pré-caché, servi en *NetworkFirst*). Si une seule variable obligatoire manque (y compris les trois `VITE_AUTH_*` inutilisées par le frontend), la configuration entière est ignorée **sans erreur visible**. | [03](03-frontend-pwa.md), [11](11-configuration.md) |
| E7 | Mise à jour de l'application : la nouvelle version attend que la page l'active. Une version déjà chargée continue de tourner tant que l'agent ne recharge pas : **le backend doit rester compatible avec elle**. Hors ligne, aucun rechargement n'a lieu. | [03](03-frontend-pwa.md), [12](12-exploitation-et-supervision.md) |
| E8 | L'URL du backend vient de `env.js`, relu à chaque chargement en ligne ; hors ligne, l'appareil garde l'`env.js` en cache, donc l'ancienne URL. Un changement de domaine du backend impose de garder l'ancien joignable (ou redirigé) le temps que tous les appareils se reconnectent. | [08](08-synchronisation-hors-ligne.md) |
| E9 | Le stockage objet doit être **joignable depuis les navigateurs** (dépôt direct par URL pré-signée, CORS) avec le même nom d'hôte que celui utilisé par le backend. Style « path », région `us-east-1` codés en dur. | [07](07-donnees-externes-et-stockage.md) |
| E10 | Les données hors ligne et l'installation PWA sont liées à l'**origine** : changer le domaine du frontend fait perdre les écritures non synchronisées des agents. C'est la raison d'être de [crvif-redirection](../crvif-redirection), dont la version servie en production diffère du dépôt (renvoi vers `/inscription`). | [14](14-migration-vers-infra-ministere.md) |
| E11 | Import POP : `pop_immeubles` est toujours mis à jour, `pop_objets` **seulement si la table est vide**. Les notices supprimées de POP ne le sont jamais ici. Avec `FORCE_REFETCH_POP=true`, l'import **bloque le démarrage**. Aucune tâche planifiée n'existe. `pop_images` est vide : les images POP ne sont pas affichées. | [07](07-donnees-externes-et-stockage.md) |
| E12 | Les fichiers importés sont `merimee.csv` et `palissy.csv` (séparateur `|`). Les en-têtes, mis en minuscules, doivent correspondre **exactement** aux noms des colonnes ; les colonnes inconnues sont ignorées sans message. | [07](07-donnees-externes-et-stockage.md) |
| E13 | `UP_API_MODE` vaut `mock` par défaut : sans `UP_API_MODE=live` et `UP_API_KEY`, la production servirait les unités patrimoniales de test. L'API Dataspace n'est joignable que depuis le réseau de production. | [11](11-configuration.md) |
